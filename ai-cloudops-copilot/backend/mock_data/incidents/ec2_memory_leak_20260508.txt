INCIDENT REPORT: EC2 MEMORY LEAK
Date: 2026-05-08 09:20:00 UTC
Service: EC2 (i-0b7c2d1f5e9a3c8b) — Background Job Worker
Region: us-west-2
Severity: HIGH

SYMPTOMS:
- Memory utilization increased from 45% to 92% over 6 days
- No recent code changes
- Instance had not been restarted in 89 days
- Job processing latency increased from 5 seconds to 35 seconds
- Out-of-memory killer (OOMkiller) started terminating worker processes
- Jobs began failing with "Cannot allocate memory" errors

ROOT CAUSE:
- Python worker process accumulating unclosed file handles
- Long-running tasks (ETL batch jobs) reading large CSV files without explicit close()
- Pandas DataFrames cached in application memory without garbage collection
- Memory fragmentation preventing reuse of freed blocks
- Process resident set size (RSS) grew by ~200MB per 1000 jobs processed

INVESTIGATION STEPS:
1. Connected to instance and ran 'free -h' — showed 28.2GB of 32GB used
2. Used 'ps_mem.py' to identify largest processes
3. Profiled Python process with 'memory_profiler' on sample jobs
4. Found DataFrame objects retained in cache dictionary indefinitely
5. Reviewed worker restart policy — restart jobs never triggered for >89 days
6. Checked application configuration — no memory limit set

RESOLUTION:
1. Implemented graceful worker restart every 12 hours
2. Added explicit file handle cleanup in job processor (with statement)
3. Limited in-memory cache to 500MB with LRU eviction
4. Deployed updated worker code v1.4.2
5. Manually restarted worker processes via deployment automation
6. Memory usage dropped to 38% within 10 minutes
7. Job latency returned to 4.8 seconds average

TOTAL DOWNTIME: 8 minutes (graceful restart)
JOBS FAILED: 94 jobs in retry queue
PREVENTION: Added memory monitoring alerts and auto-restart thresholds
